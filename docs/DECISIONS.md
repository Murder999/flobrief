# PostPiloter — Technical Decisions Log

## Part 1 — Foundation

### DECISION-001: Monorepo with apps/ structure
**Decision**: Use `apps/backend` and `apps/frontend` in a single git repo with `packages/shared` for future shared types.  
**Reason**: Team coordination, atomic commits across stack, shared CI pipeline. No complex Nx/Turborepo tooling at this scale — plain directory structure with Makefile scripts.  
**Trade-off**: Less isolation than polyrepo, but simpler operations for a 2-layer stack.

### DECISION-002: FastAPI over Django REST Framework
**Decision**: Use FastAPI for the backend API.  
**Reason**: Async-first (asyncpg + SQLAlchemy async), automatic OpenAPI docs, Pydantic native, lower overhead. DRF would require significant async adaptation.  
**Trade-off**: Less built-in admin panel (not needed — we build our own).

### DECISION-003: SQLAlchemy 2.x Async over Tortoise ORM / Databases
**Decision**: SQLAlchemy 2.x with asyncpg driver.  
**Reason**: Industry standard, mature ecosystem, excellent Alembic integration, full Python type support.  
**Trade-off**: Slightly more boilerplate than Tortoise, but vastly better tooling and community support.

### DECISION-004: Next.js App Router
**Decision**: Use Next.js 14+ with App Router (not Pages Router).  
**Reason**: Server Components, built-in layouts, nested routing for (auth)/(dashboard) groups, better caching semantics.  
**Trade-off**: Newer patterns, some libraries not yet fully compatible with RSC — mitigated by keeping state libraries to minimum.

### DECISION-005: Dark-first UI (near-black background)
**Decision**: UI primary background is #0A0A0F (near-black), not white or light gray.  
**Reason**: Premium SaaS positioning, brand differentiation, aligns with Linear/Raycast aesthetic. Target users (agency professionals) work long hours — dark mode reduces fatigue.  
**Trade-off**: Light-mode-first is more accessible for some users; we will add system-preference detection and optional light theme in Part 14.

### DECISION-006: UUID primary keys throughout
**Decision**: All tables use UUID v4 as primary key, generated by PostgreSQL.  
**Reason**: Prevents enumeration attacks, safe for sharding, no sequential ID leakage in URLs.  
**Trade-off**: Slightly larger index size vs. BIGSERIAL. Negligible at our scale.

### DECISION-007: Soft deletes on all core tables
**Decision**: Use `deleted_at TIMESTAMPTZ NULL` instead of hard deletes.  
**Reason**: Audit trail, data recovery, billing dispute resolution, compliance.  
**Trade-off**: All queries must include `WHERE deleted_at IS NULL` filter — enforced at service layer, not ORM level. Risk of accidental data leak if filter forgotten — mitigated by base service class that always applies the filter.

### DECISION-008: Python Ruff for linting/formatting
**Decision**: Use Ruff (not flake8 + black + isort separately).  
**Reason**: Extremely fast, single tool for lint + format, covers all the rules we need.

### DECISION-010: platform_admin as a third user type, tenant-independent
**Decision**: `users` tablosuna `user_type VARCHAR(20) DEFAULT 'tenant_user'` kolonu eklendi.
Değerler: `tenant_user` | `platform_admin`. Platform admin için ayrı tablo açılmadı.
Tüm güvenlik detayları `docs/PLATFORM_ADMIN_SECURITY.md`'de belgelenmiştir.  
**Reason**: Platform genelinde tüm ajans, kullanıcı, abonelik ve sistem loglarını yönetecek
tenant-bağımsız bir süper yönetici katmanı gereklidir. Bu katmanın kendi tenant'ı yoktur;
JWT'sinde `agency_id` bulunmaz; tenant endpoint'lerine erişemez.  
**Trade-off**: Ayrı `platform_admins` tablosu daha güçlü izolasyon sağlardı ama iki paralel
auth sistemi ve duplicate şifre/soft-delete kodu yaratırdı. `user_type` kolonu + service
layer guard + ayrı endpoint namespace yeterli izolasyonu sağlar.  
**Güvenlik notları**:
- Oluşturma: yalnızca `scripts/create_platform_admin.py` CLI — kayıt/davet akışı yok
- JWT ömrü: access 5 dk, refresh 8 saat (tenant'tan kısa)
- MFA/TOTP zorunlu (Part 13)
- Tüm eylemler immutable `platform_audit_logs`'a yazılır
- Impersonation açıkça loglanır; sessiz değil
- IP allowlist + ayrı rate limit bucket

### DECISION-011: platform_admin UI paneli Part 13'e taşındı (billing'den önce)
**Decision**: Orijinal Part 13 (billing/iyzico) → Part 14'e kaydırıldı.
Part 13 = Platform Admin Dashboard + MFA + impersonation + tenant management + platform analytics.  
**Reason**: Admin güvenlik altyapısının (MFA, audit, IP allowlist) billing'den önce prod'a girmesi
gerekiyor. Billing, admin panelin tenant management'ına bağımlıdır (plan assignment, manual override).  
**Trade-off**: iyzico entegrasyonu bir part ertelendi; ancak güvenlik önce gelir ve sıralama
bağımlılık açısından da daha doğrudur.

## Part 3 — Auth, JWT, Refresh Tokens

### DECISION-012: UserToken model instead of separate RefreshToken model
**Decision**: Single `user_tokens` table stores refresh tokens, email verification tokens, and password reset tokens, unified by `token_type` enum (`refresh | email_verify | password_reset`).  
**Reason**: Avoids three separate migration/model/repository files for functionally similar token patterns. Same revocation, expiry, and cleanup logic applies to all token types.  
**Trade-off**: Query filters must always include `token_type`. Mitigated by repository methods that bake in the type constraint.

### DECISION-013: Refresh token rotation with family-based reuse detection
**Decision**: Every refresh token has a `token_family` UUID. On rotation, old token is revoked and a new one issued in the same family. If a revoked token is presented again, the entire family is revoked (full logout).  
**Reason**: Defends against refresh token theft and replay. If an attacker steals a refresh token, its reuse triggers family revocation, alerting the legitimate user.  
**Trade-off**: A network failure during rotation can cause the client to lose its only refresh token. Mitigated by: client retries the same token (idempotent on the second use within a short window is a future improvement; for now, user must log in again).

### DECISION-014: SHA-256 hash stored in DB, plaintext only to client
**Decision**: `token_hash` column stores `hashlib.sha256(plaintext.encode()).hexdigest()` (64 hex chars). Plaintext is never written to the database.  
**Reason**: If the `user_tokens` table is leaked, stored hashes are useless without brute-force on a 384-bit random token (secrets.token_urlsafe(48)). Pre-image resistance of SHA-256 makes this infeasible.  
**Trade-off**: SHA-256 is fast — mitigated by the 384-bit token length (brute force is computationally infeasible regardless of hash speed).

### DECISION-015: Platform admin login is a separate service method and endpoint
**Decision**: `AuthService.platform_admin_login()` is distinct from `AuthService.login()`. Platform admin gets a separate httpOnly cookie (`platform_refresh_token`, path=`/api/v1/platform/auth`, samesite=strict).  
**Reason**: Different token lifetimes (5min/8hr vs 15min/30day), mandatory audit logging to `platform_audit_logs`, and cookie path isolation (prevents platform admin cookie from being sent to tenant endpoints).  
**Trade-off**: Code duplication in token creation logic — acceptable as the security isolation benefit outweighs DRY concerns here.

### DECISION-016: Email sending is fire-and-forget via contextlib.suppress
**Decision**: All email sends are wrapped in `with contextlib.suppress(Exception):` — failures are silently swallowed.  
**Reason**: Email delivery failure (SMTP down, MailHog unavailable in dev) must never block auth flows. Verification emails can be resent; password reset links can be re-requested.  
**Trade-off**: Email failures are invisible in logs. Future improvement: structured log warning before suppress (Part 9 observability).

### DECISION-017: RegisterRequest has no user_type field
**Decision**: The `RegisterRequest` schema does not expose a `user_type` field. All registrations create `agency_user`. `platform_admin` can only be created via CLI script.  
**Reason**: Prevents any path where an attacker can request platform admin privileges via the public API.  
**Trade-off**: None — this is a strict security requirement, not a trade-off.

## Part 4 — RBAC, Workspace, Invitation System

### DECISION-018: Flat Permission enum with namespace prefixes
**Decision**: Permissions are flat string constants (`agency:view`, `platform:manage_tenants`) in a single enum, not a nested role hierarchy.  
**Reason**: Simpler dependency injection — `require_permission(Permission.AGENCY_VIEW)` is a single FastAPI dependency. Role-to-permission mapping is a frozenset dict, fail-closed (unknown roles → empty frozenset).  
**Trade-off**: More verbose permission list than a simple role check; justified by fine-grained control.

### DECISION-019: WorkspaceContext resolved via X-Agency-ID header
**Decision**: All tenant-scoped endpoints receive agency context via `X-Agency-ID` request header, not JWT claims.  
**Reason**: A user can be a member of multiple agencies. The header lets the client switch workspace without re-issuing a JWT. The dependency validates membership on every request (server-side, not just frontend hiding).  
**Trade-off**: Extra DB lookup per request for membership validation — acceptable; will be cached in Redis in Part 10.

### DECISION-020: Invitation revoke/resend by ID for admin operations
**Decision**: Admin-facing revoke/resend use `POST /invitations/{id}/revoke|resend` (invitation UUID). The token-based endpoints (`/revoke/{token}`, `/resend/{token}`) remain for compatibility but are not used in admin UI.  
**Reason**: Admin invitation list only returns `InvitationRead` (no plaintext token — only hash is stored). Exposing the hash would be a security regression. ID-based endpoints enforce the same authorization (owner/admin role check) without requiring token exposure.  
**Trade-off**: Two sets of revoke/resend endpoints; the token-based ones can be deprecated in Part 15.

### DECISION-021: platform_admin blocked at get_workspace_context dependency
**Decision**: `get_workspace_context()` raises 403 immediately if `user.user_type == "platform_admin"`. Platform admins cannot access any tenant endpoint, even if they somehow have an agency member record.  
**Reason**: Defense in depth — service layer also blocks it, but the dependency-level check prevents any code from reaching the endpoint handler.  
**Trade-off**: None — this is a hard requirement.

## Part 5 — Dynamic Brief Template Engine

### DECISION-022: Relational tables for template/section/field hierarchy
**Decision**: BriefTemplate, BriefTemplateSection, BriefTemplateField are separate relational tables, not a single JSONB column on BriefTemplate.  
**Reason**: Enables per-field and per-section queries (sort_order reorder, uniqueness constraint enforcement, JOIN for field_key lookup), and keeps schema evolution simpler. JSONB used only for `options` and `validation_rules` (leaf-level, unstructured).  
**Trade-off**: More joins than JSONB; acceptable — template detail is always loaded as one unit.

### DECISION-023: System templates with agency_id=NULL
**Decision**: System templates have `agency_id=NULL, is_system_template=True`. Agency templates have `agency_id=<uuid>, is_system_template=False`. No separate table.  
**Reason**: Shared table simplifies list queries (one query with OR condition). `is_system_template` flag prevents modification by tenant endpoints. System templates are visible to all agencies.  
**Trade-off**: NULL FK requires application-level guard; the service layer enforces `_assert_template_owned_by_agency` for all mutation paths.

### DECISION-024: field_key uniqueness enforced at service layer (per template, not per section)
**Decision**: DB has `UNIQUE(section_id, field_key)` constraint, but service validates uniqueness across the entire template (all sections) before inserting.  
**Reason**: Brief form rendering uses `field_key` as the answer key. If two sections had the same `field_key`, the answer map would collide. DB constraint is per-section; business rule is per-template.  
**Trade-off**: Extra SELECT before INSERT; worth it to maintain unambiguous brief answer keys.

### DECISION-025: TemplateBuilder frontend uses in-memory state, not optimistic updates
**Decision**: Template editor mutates local React state after confirmed API responses (no optimistic UI). Save is explicit for meta fields; section/field changes are immediate.  
**Reason**: Template builder is not a real-time collaborative tool. Reliability over speed. Error states are simpler to handle.  
**Trade-off**: Slight latency on add/edit/delete actions; acceptable for an admin tool.

## Part 6 — Brief CRUD & Industry Templates

### DECISION-026: BriefFieldValue stored as JSONB upsert
**Decision**: Brief field answers are stored as individual rows in `brief_field_values` (one row per field), using PostgreSQL `INSERT ... ON CONFLICT DO UPDATE` for saves.  
**Reason**: Allows partial saves (save section by section), enables per-field indexing in future, and avoids re-fetching entire brief to merge. Upsert eliminates the need to check existence before write.  
**Trade-off**: More rows than a single JSONB column on the brief; justified by flexibility and partial-save capability.

### DECISION-027: Status transitions enforced in service layer dict
**Decision**: `_STATUS_TRANSITIONS` dict in `BriefService` defines valid next states per current state. Any transition not in the dict is rejected with HTTP 422.  
**Reason**: Business logic must live in the service, not the API layer or database triggers. The dict is easy to audit and extend (e.g., adding "recalled" state later).  
**Trade-off**: Status stored as plain String(30) not a DB ENUM — avoids migration cost of altering a PostgreSQL enum type when states change.

### DECISION-028: System template seeds via Alembic migration (not fixture file)
**Decision**: 10 industry system templates (with sections + fields) are seeded inside the Alembic `upgrade()` function using `op.get_bind()`.  
**Reason**: Seeds must run atomically with schema creation. A separate seed file or CLI command risks running out of order. Idempotency check (`COUNT(*) WHERE is_system_template`) prevents double-seeding.  
**Trade-off**: Migration files grow larger; acceptable since template data is stable and not environment-specific.

### DECISION-029: DynamicBriefForm as stateful client component (no autosave)
**Decision**: `DynamicBriefForm` maintains local state and requires explicit "Kaydet" click. No autosave timer.  
**Reason**: Autosave requires debounce + conflict detection; adds complexity without clear UX benefit for brief forms (unlike notes/docs). Explicit save shows `savedAt` timestamp for user confidence.  
**Trade-off**: User can lose changes if navigating away; future Part can add `beforeunload` guard.

## Part 7 — Versioning & Approval Portal

### DECISION-030: SHA-256 token hashing — raw token never persisted
**Decision**: `secrets.token_urlsafe(48)` generates the raw token; `hashlib.sha256(raw.encode()).hexdigest()` is stored in `approval_tokens.token_hash`. The raw token is returned once to the caller and embedded in `approval_url`. It is never stored or logged.  
**Reason**: If the DB is compromised, approval links cannot be replayed. 48-byte urlsafe entropy is 384 bits — brute force is infeasible.  
**Trade-off**: Token cannot be recovered if lost; caller must copy it on first use. Acceptable because the agency can revoke and resend.

### DECISION-031: JSONB snapshot on approval submission
**Decision**: `send_to_approval()` builds a full JSONB snapshot of the brief (title, description, priority, deadline, brand name, template name, all section+field metadata, all field values) and stores it in `brief_versions.snapshot`.  
**Reason**: Brief fields can be edited between approval cycles. The approver must see exactly what was sent to them, not the current state. The snapshot is also served on the public portal.  
**Trade-off**: Snapshot data is denormalized and grows with each version. Acceptable since approval cycles are infrequent and data is compact JSON.

### DECISION-032: Public portal is a standalone Next.js route with no auth context
**Decision**: `/approve/[token]` uses its own layout (no AuthProvider dependency), calls `publicApprovalApi` directly, and renders without any dashboard chrome.  
**Reason**: Brand approvers do not have Flobrief accounts. The portal must be accessible via a raw URL, be mobile-first, and visually represent the agency's professionalism.  
**Trade-off**: Cannot share dashboard components that depend on auth context; acceptable since the portal has its own premium visual design.

### DECISION-033: `event_metadata` column name instead of `metadata`
**Decision**: `ApprovalEvent.event_metadata` (not `metadata`) is used for the JSONB audit payload.  
**Reason**: `metadata` is a reserved attribute in SQLAlchemy's Declarative API (`Table.metadata`). Using it as a mapped column name raises `InvalidRequestError` at class definition time.  
**Trade-off**: Slightly less idiomatic column name, but correctly avoids the ORM conflict.

### DECISION-034: Approval sidebar in brief detail (not inline or modal)
**Decision**: The approval panel (send button, URL display, history, versions) is a collapsible sidebar column on `/dashboard/briefs/[id]` using CSS grid `lg:grid-cols-3`.  
**Reason**: Approval is a distinct workflow from brief content editing. Placing it in a sidebar keeps the main content column uncluttered while keeping context visible.  
**Trade-off**: On mobile the sidebar stacks below the form — acceptable since approval actions are less frequent on mobile.

## Part 8 — Comments, Threads & Asset Management

### DECISION-035: CommentThread + Comment two-level hierarchy (not flat)
**Decision**: `comment_threads` wraps a group of `comments`, not a flat comment table per-brief.  
**Reason**: Allows resolve/reopen at thread level, groups related replies, and lets each thread be anchored to a brief, field, asset, or approval without duplicating anchor logic on every comment.  
**Trade-off**: Two table JOINs to list comments for a brief — acceptable; volume is low and threads are always loaded with their comments together.

### DECISION-036: comment_threads.asset_id has NO FK constraint
**Decision**: `asset_id` stored as plain UUID column; service layer validates asset ownership.  
**Reason**: Circular FK between `comment_threads` ↔ `assets` (assets can have threads; threads can reference assets) would require deferred constraints. Service-layer validation is simpler and avoids migration ordering issues.  
**Trade-off**: DB allows invalid asset_id — protected by service guard `_require_asset()`.

### DECISION-037: StorageBackend ABC for cloud-readiness
**Decision**: `StorageBackend` ABC with `save`, `delete`, `get_path` methods; `LocalStorageBackend` implements it; `get_storage_backend()` factory reads `settings.STORAGE_BACKEND`.  
**Reason**: S3/R2 migration requires only a new class implementation, not API or service changes.  
**Trade-off**: Abstraction overhead for what is currently only local storage — justified by inevitable cloud migration.

### DECISION-038: File delete is soft (DB only) — storage file retained
**Decision**: `asset.soft_delete()` marks deleted in DB; file on disk/S3 is not removed.  
**Reason**: Audit trail, version referencing, and potential undelete. Storage cleanup can be a background job.  
**Trade-off**: Storage grows without periodic GC. Acceptable at current scale; garbage collection added in Part 15.

### DECISION-039: 204 responses via Response(status_code=204) from function body
**Decision**: FastAPI 0.115 DELETE endpoints that need 204 do NOT set `status_code=204` in the decorator. Instead they return `Response(status_code=204)` from the function body.  
**Reason**: FastAPI 0.115 asserts `is_body_allowed_for_status_code(status_code)` at route registration time; for 204 this returns False and raises AssertionError. Returning a `Response` object directly bypasses this assertion while still delivering 204 to the client.  
**Trade-off**: OpenAPI schema for these endpoints shows 200 as default; acceptable since the actual HTTP response is 204.

## Part 9 — Content Calendar

### DECISION-040: CalendarItemStatusHistory is append-only (no soft-delete)
**Decision**: `CalendarItemStatusHistory` records are never soft-deleted; service layer does not call `soft_delete()` on them.  
**Reason**: Status change history is an immutable audit trail. Soft-deleting history rows would break the audit log and allow retroactive timeline manipulation.  
**Trade-off**: History table grows indefinitely per item — acceptable; items are deleted eventually via CASCADE.

### DECISION-041: CalendarItemType.EMAIL and CalendarPlatform.EMAIL share value "email"
**Decision**: Both enums have a member with string value "email". No conflict because they are separate Python enum classes.  
**Reason**: "email" is both a valid content type (email campaign) and a valid delivery platform. Treating them independently enables proper filtering on each axis.  
**Trade-off**: Slightly surprising for developers new to the codebase — documented here.

### DECISION-042: Calendar deferred FK on asset_links applied in Part 9 migration
**Decision**: `asset_links.calendar_item_id → calendar_items.id` FK was intentionally left without a DB constraint in the Part 8 migration, and the constraint was added in the Part 9 Alembic migration (b2c3d4e5f6g7).  
**Reason**: `calendar_items` table did not exist in Part 8. The column was added first with no constraint; the FK was backfilled in the next migration after the table was created.  
**Trade-off**: Brief window between Part 8 and Part 9 migrations where the column existed without the FK — acceptable in sequential migration flow.

### DECISION-043: Calendar views use ISO Mon-first week calculation
**Decision**: Week view uses Monday as week start; week number calculated as ISO week (via `getDay() || 7` pattern in frontend; Python `calendar.monthrange` for month).  
**Reason**: European/Turkish calendar convention; agencies using Flobrief are predominantly Turkish. ISO week numbering matches Python's `date.isocalendar()`.  
**Trade-off**: Differs from US Sunday-start conventions; acceptable for target market.

### DECISION-044: ActivityLog extends Base directly (not BaseModel) — immutable audit trail
**Decision**: `ActivityLog` inherits `Base` instead of `BaseModel`. It has no `updated_at`, no `deleted_at`, no `soft_delete()`.  
**Reason**: Activity logs are forensic records. Allowing update or soft-delete would undermine their integrity as an audit trail. No FK constraints on agency_id/brand_id/actor_user_id so that deleting entities never removes historical log entries.  
**Trade-off**: ActivityLog does not benefit from the shared `deleted_at` filtering convention — repositories must not expose update/delete methods.

### DECISION-045: TemplateRenderer uses stdlib string.Template + html.escape instead of Jinja2
**Decision**: Email/WhatsApp template rendering uses Python stdlib `string.Template.safe_substitute()` + `html.escape()`. Jinja2 is not used.  
**Reason**: Jinja2 is not in pyproject.toml dependencies (FastAPI makes it optional). Adding it just for simple variable substitution in email templates would be an unnecessary dependency. stdlib is sufficient and has no XSS risk when combined with `html.escape()`.  
**Trade-off**: No loops or conditionals in templates — intentional. Complex template logic goes in Python, not in DB-stored template strings.

### DECISION-046: PassiveWhatsAppProvider — architecture-ready but no Meta API calls
**Decision**: `PassiveWhatsAppProvider.send()` always returns `status="passive"` without making any HTTP call to Meta/WhatsApp APIs. `is_configured` returns False when `WHATSAPP_API_TOKEN` is empty.  
**Reason**: Meta WhatsApp Business API requires phone number registration, message template pre-approval, and production approval — none of which is available in the current dev/staging environment. Building the full architecture now (delivery records, channel enum, preference toggle) avoids future breaking changes.  
**Trade-off**: WhatsApp notifications silently no-op in all environments until an operator configures the token — this is the intended behavior and is documented in the UI.

## Part 11 — Reporting & Secure Report Links

### DECISION-047: ReportSnapshot immutability for forensic accuracy
**Decision**: `ReportSnapshot` stores a frozen JSONB copy of metrics at generation time. Regenerating a report creates a new snapshot; it never mutates the old one.  
**Reason**: Shared reports must be stable — if a client receives a report link, the data they see must not change because a brief was later approved. Immutable snapshots also serve as audit evidence.  
**Trade-off**: Report data can go "stale" between the period end and the viewing date — users must explicitly click "Regenerate" to refresh. This is intentional, not a bug.

### DECISION-048: SHA-256 token hashing for share tokens (same pattern as approval tokens)
**Decision**: Raw share token (`secrets.token_urlsafe(48)`) is returned once on creation and never persisted. Only `hashlib.sha256(raw.encode()).hexdigest()` is stored in DB.  
**Reason**: Consistent with the approval token security pattern. If the DB is breached, attackers cannot use token hashes to access reports — they must have the raw token (which was only ever in the HTTP response, not in any DB column).  
**Trade-off**: Token recovery is impossible — a new token must be issued if lost. This is the intended behavior.

## Part 6A — WhatsApp Real Provider Completion + Controlled Test Send

### DECISION-049: WhatsApp opt-in without a phone-verification (OTP) flow
**Decision**: `users.phone_verified_at` exists as a schema column but no OTP/SMS-verification flow is built. WhatsApp consent is self-attested: a user enters their own phone number and explicitly flips the `whatsapp_enabled`/`whatsapp_opt_in` toggle in their profile — that combination is the entire consent mechanism, gated further by `Agency.is_demo` (always blocks real sends) and, for the controlled test-send endpoint specifically, by requiring the target phone to be either the requesting user's own opted-in `phone_number` or the platform's fixed `WHATSAPP_TEST_RECIPIENT` allowlist (non-production only) — never a caller-supplied number.  
**Reason**: Building a full OTP verification flow is a separate feature, out of scope for Part 6A, which is about completing the provider/template/delivery plumbing and a single controlled test send. Leaving `phone_verified_at` silently unenforced (as it was before this decision) would violate the "no silent/ambiguous policy" requirement — this document makes the policy explicit instead.  
**Trade-off**: A user could enter a phone number they don't actually control and opt in on it — the same trust model already implicit in normal Twilio WhatsApp sandbox-style products before a formal verification step is added. `phone_verified_at` remains reserved for a future OTP flow; when built, it should additionally gate the `whatsapp_enabled` toggle.

### DECISION-050: Approved-template gate applies only to the new test-send flow, not the existing event dispatcher
**Decision**: `WhatsAppTemplateRepository.get_approved()` (approval-status + `content_sid` gating) is enforced only in the new `POST /api/v1/notifications/whatsapp/test` flow. The existing `NotificationDispatcher` per-event WhatsApp path (`brief.created`, `comment.added`, etc.) continues to send free-text messages via `whatsapp_template_service.py`, unchanged.  
**Reason**: Event→template mapping (assigning a real Twilio-approved Content SID to each of the ~40 Flobrief notification event types) is explicitly Part 6B scope. Gating the dispatcher now — before any event has an approved template — would turn every real event-driven WhatsApp notification into `skipped_template_missing`, a behavior change to already-working code outside this part's stated scope. Confirmed with the user before implementation.  
**Trade-off**: Free-text event notifications sent via Twilio Sandbox/session-window messaging today are not compliant with real Meta WhatsApp Business API template requirements outside a 24-hour session window — this is a known, explicitly deferred gap closed in Part 6B, not a regression introduced here.

### DECISION-051: `whatsapp_templates` table repurposed into the approved-template registry (not a new table)
**Decision**: The pre-existing, unused `WhatsAppTemplate` model/table (originally built for the abandoned `PassiveWhatsAppProvider` design — DECISION-046) was extended in place with `event_type`, `provider`, `content_sid`, `status`, `variable_schema`, `updated_by_id`, `approved_at` columns, rather than creating a second, parallel template table.  
**Reason**: An audit confirmed the table had zero repository/service/route references anywhere in the codebase — genuinely orphaned. Repurposing avoids a duplicate, confusingly-named second template concept.  
**Trade-off**: The migration drops the old unused `is_active` column in favor of the new `status` enum; there was no data to migrate since the table was empty in every environment.

### DECISION-049: fpdf2 with TTF font detection + Latin-1 transliteration fallback
**Decision**: PDF generation uses `fpdf2==2.8.3`. At module load time, `_detect_unicode_font()` checks for system TTF fonts (Arial on Windows, DejaVuSans on Linux). If found, the font is registered as `MainFont`/`MainFontBold` via `add_font()`. If not found, Helvetica (Latin-1 core font) is used with `_s()` transliteration (`ş→s`, `ğ→g`, `ı→i`, `İ→I`, `…→...`).  
**Reason**: fpdf2's bundled core fonts only support Latin-1 (ISO 8859-1). Turkish characters ş, Ş, ğ, Ğ, ı, İ are in Latin Extended-A (U+0130–U+017F), outside Latin-1. TTF loading solves this correctly; transliteration is the safe fallback for CI/Docker environments without system fonts.  
**Trade-off**: On systems without TTF fonts, Turkish characters are degraded to ASCII equivalents. Quality is lower but functional. In production Docker images, DejaVuSans-ttf package should be installed for correct rendering.

## Part 12 — White-Label Branding

### DECISION-050: SVG rejected for branding uploads
**Decision**: SVG files are explicitly rejected for logo/favicon uploads even though `ALLOWED_MIME_TYPES` in storage_service.py includes `image/svg+xml`.  
**Reason**: SVG files can contain JavaScript, `<script>` tags, and event handlers. When served as branding assets (publicly accessible), a malicious SVG could execute XSS attacks in the browser context of the approval/report public pages.  
**Trade-off**: Agencies with SVG-only logos must convert to PNG/WebP. This is acceptable because SVG-to-raster conversion is trivial and the security risk is non-negotiable.

### DECISION-051: Branding asset public endpoint with ownership guard
**Decision**: `/api/v1/public/branding/assets/{asset_id}` is a public endpoint (no auth required) but only serves assets that have a `BrandingAsset` record, verified by a DB lookup before serving.  
**Reason**: Logos and favicons must be publicly accessible for unauthenticated approval/report portals. However, allowing any asset UUID to be fetched publicly would expose all agency assets. The `BrandingAsset` junction table acts as an explicit allowlist of publicly-servable files.  
**Trade-off**: One extra DB query per public asset fetch. Acceptable at this scale; in production these are CDN-served anyway.

### DECISION-052: White-label entitlement enforced at service layer
**Decision**: `is_white_label_enabled` can only be set to `true` in `BrandingService.update_settings()` if `plan.white_label_enabled=True`. The frontend also shows a locked state but this is defense-in-depth only.  
**Reason**: Client-side entitlement checks are easily bypassed. The service layer is the single authoritative enforcement point. The check does a live `SELECT Plan JOIN Subscription` query at request time, not from cached JWT claims.  
**Trade-off**: One extra DB query per branding update. Correct behavior is more important than micro-optimization here.

### DECISION-053: Public branding returns is_branded=False when entitlement disabled
**Decision**: The public branding endpoints (`/by-approval-token`, `/by-report-token`) return a valid 200 response with `is_branded=false` and null colors/logo when white-label is not enabled, rather than 404 or 403.  
**Reason**: The public portal always calls this endpoint to determine branding. A 4xx response would require the portal to special-case error handling. Returning `is_branded=false` lets the portal fall back to default Flobrief branding seamlessly.  
**Trade-off**: Slightly more data returned than necessary in the common case (no branding). The response payload is tiny so this is irrelevant.

### DECISION-054: Custom domain verification token hashed (SHA-256)
**Decision**: Domain verification tokens follow the same SHA-256-only storage pattern as approval tokens and report share tokens. Raw token returned once, hash stored.  
**Reason**: Consistent security model across all token types. A leaked DB backup should not expose any raw tokens that give access to resources or actions.  
**Trade-off**: If the token is lost, a new one must be generated (via re-POSTing). This is acceptable UX.

### DECISION-009: iyzico for payment (Turkey market)
**Decision**: iyzico as payment processor for Part 14.  
**Reason**: Turkish market primary target, iyzico is the de-facto standard for Turkish SaaS businesses, supports 3D Secure and local payment methods.  
**Trade-off**: Not available for international expansion without adding Stripe later.

## Part 14 — Billing & Entitlements

### DECISION-055: iyzico CheckoutForm — card data never touches Flobrief servers
**Decision**: All checkout sessions use iyzico CheckoutForm model (hosted payment page). Flobrief never receives card numbers, CVV, or PAN.  
**Reason**: PCI-DSS compliance — iyzico is the PCI-certified endpoint; our server never sees card data. This eliminates the most serious class of payment security risks.  
**Trade-off**: Users are redirected to iyzico-hosted page; less control over payment UX. The security benefit outweighs the UX trade-off.

### DECISION-056: Webhook idempotency via provider_event_id UNIQUE constraint
**Decision**: `billing_events.provider_event_id` has a DB UNIQUE constraint. Incoming webhooks that match an existing processed event are skipped before any side effects.  
**Reason**: iyzico may retry webhooks on network failure. Without idempotency, a subscription could be activated/cancelled multiple times, causing double-invoicing or incorrect status.  
**Trade-off**: Events without a provider_event_id (malformed payloads) are processed without idempotency protection — acceptable since they're logged as PENDING/FAILED.

### DECISION-057: Entitlement enforcement at service layer, not JWT claims
**Decision**: EntitlementService does a live `SELECT Plan JOIN Subscription` query at each operation. Plan limits are not cached in JWT or application memory.  
**Reason**: Plan downgrades must take effect immediately without requiring re-login. JWT-cached entitlements would allow a downgraded user to continue using premium features until token expiry.  
**Trade-off**: One extra DB query per entitled operation (brand create, user invite, template create). Acceptable — these are low-frequency mutation operations.

### DECISION-058: Sandbox mode when iyzico API keys are empty
**Decision**: When `IYZICO_API_KEY` or `IYZICO_SECRET_KEY` is empty, `IyzicoProvider.is_configured()` returns False and `BillingService.create_checkout_session()` returns a simulated response with `sandbox=True`.  
**Reason**: Development environments shouldn't require real iyzico credentials. The simulated response has the same schema as the real one, allowing frontend billing UI to be developed and tested without payment infrastructure.  
**Trade-off**: Sandbox mode looks identical to real checkout except for the `sandbox: true` flag — developers must check this flag to confirm they're not accidentally in sandbox mode in production.

### DECISION-059: contextlib.suppress for best-effort iyzico cancellation
**Decision**: `BillingService.cancel_subscription()` uses `contextlib.suppress(IyzicoError)` around the iyzico API call. If iyzico returns an error, the local subscription is still marked CANCELLED.  
**Reason**: Subscription cancellation in our DB must be reliable regardless of iyzico API availability. The customer's intent (cancel) should be honored even if iyzico temporarily fails. The iyzico subscription will expire naturally.  
**Trade-off**: In theory, a customer could still be charged if our DB says cancelled but iyzico doesn't know. In practice, iyzico has its own cancellation UI and the customer can confirm there too.

## Part 15 — Final Polish & Launch Readiness

### DECISION-060: SecurityHeadersMiddleware in FastAPI (not Nginx-only)
**Decision**: Security headers (X-Content-Type-Options, X-Frame-Options, X-XSS-Protection, Referrer-Policy, Permissions-Policy, HSTS) are added by a `BaseHTTPMiddleware` in `main.py`, not only in nginx.conf.  
**Reason**: Defense in depth. Backend responses have headers even when accessed directly (bypassing Nginx in dev/staging). HSTS is only emitted when `settings.APP_ENV == "production"` to avoid pinning localhost.  
**Trade-off**: Middleware runs on every request including health checks. Performance impact is negligible (pure header mutation, no IO).

### DECISION-061: Toast/Confirm modal replaces browser `confirm()`
**Decision**: All `window.confirm()` / `confirm()` calls removed and replaced with `useToast().confirm()` — a Promise-based modal rendered in React.  
**Reason**: `confirm()` is blocked in cross-origin iframes, not style-able, and inconsistent across browsers. Premium SaaS UX requires in-app confirmation modals.  
**Trade-off**: `useToast()` must be called within a component tree that has `<ToastProvider>`. Error if called outside — caught at development time.

### DECISION-062: Security audit tests are DB-agnostic
**Decision**: `test_security_audit.py` tests only the authentication/middleware layer without requiring a live database.  
**Reason**: Security properties (401 on missing/invalid token, security headers on all responses, platform admin rejection on tenant routes) are all enforced before any DB query reaches the business layer. Tests that require DB (cross-tenant data isolation at query level) are not in this file — they belong in integration tests that require a test database.  
**Trade-off**: Does not verify DB-level tenant isolation (e.g., SQL queries that accidentally return cross-tenant data). This gap is acceptable because every DB query is scoped via explicit `agency_id` WHERE clauses enforced by `get_workspace_context()`.

### DECISION-063: next.config.mjs output: "standalone" for production Docker
**Decision**: `output: "standalone"` added to Next.js config for the production Dockerfile.  
**Reason**: Standalone output creates a self-contained `server.js` with only the required `node_modules`. The resulting Docker image is ~70% smaller than a full `node_modules` install.  
**Trade-off**: Static files must be manually copied from `.next/static` to the standalone output directory (handled in the Dockerfile's `COPY` steps). Dev server is unaffected.

### DECISION-064: Demo seed uses idempotency check on agency slug
**Decision**: `seed_demo.py` exits early if `DEMO_AGENCY_SLUG` already exists. It does NOT delete and re-seed.  
**Reason**: Idempotent seeding is safe to run multiple times in CI and staging. Destructive re-seed would wipe demo data that someone may have modified (e.g., added test briefs manually).  
**Trade-off**: If the demo data becomes stale, the agency must be manually deleted from the DB before re-running the seed.

### DECISION-065: Transactional email uses Resend HTTPS API only
**Decision**: Registration, password reset, invitations, approvals, and notification delivery use Resend's HTTPS API. Production code has no SMTP fallback. A test mode routes every message to `delivered@resend.dev`, uses `onboarding@resend.dev`, and prefixes the subject with the intended recipient.
**Reason**: Railway Hobby/Trial does not provide a reliable SMTP path, while Resend test addresses safely simulate delivery without a verified domain. Missing provider configuration must never crash application flows.
**Trade-off**: Test-address messages are inspected in the Resend Dashboard rather than delivered to a real inbox. Real recipients require a verified sending domain and test mode must be disabled.

### DECISION-066: Self-service password changes revoke all sessions
**Decision**: Every user may change their own password after confirming the current password and satisfying the shared password-strength policy. Tenant users and platform admins use separate endpoints to preserve the platform security boundary. A successful change revokes all refresh tokens, clears the relevant refresh cookie, and sends the user to login again.
**Reason**: Re-authentication prevents an unattended session from changing credentials, while global refresh-token revocation ensures previously issued sessions cannot silently survive a credential change. The same accessible form is reused in agency, brand, and platform profile screens.
**Trade-off**: A password change signs the user out on every device. This is intentional security behavior rather than per-device session continuity.

### DECISION-067: Local auth uses a same-origin Next.js API rewrite
**Decision**: When `NEXT_PUBLIC_API_URL` is empty, the local Next.js server rewrites `/api/v1/*` to `http://127.0.0.1:8000/api/v1/*`. Browser code uses relative API paths in that mode. Deployed environments continue using their explicit public API URL and do not enable the rewrite.
**Reason**: Mixing a `localhost` frontend with a `127.0.0.1` API makes refresh cookies cross-site in modern browsers. The login request succeeds, but session restoration can fail and protected layouts redirect users back to login. A same-origin rewrite keeps the cookie on the frontend origin and preserves its backend-defined path.
**Trade-off**: Local development requires the backend to run on port 8000 unless the rewrite destination is changed. Production behavior is unaffected while `NEXT_PUBLIC_API_URL` is configured. (2026-07-22: corrected the destination port from a stale 8003 back to 8000 — the port had drifted out of sync with the documented default in README/.env.example/CI, which caused the local dev proxy to point at nothing, silently swallowing every `/api/v1/*` request before it reached the backend.)

### DECISION-068: Image annotation coordinates stay in the existing 0–100 percent scale
**Decision**: `DeliverableAnnotation.x_percent`/`y_percent` remain 0–100 floats (not renamed to a literal 0–1 fraction), computed against the actual rendered `object-fit: contain` image rect, not the container.
**Reason**: A full annotation backend (model, migration, agency + brand API, frontend `AnnotationCanvas`) already existed from a prior "Brand Portal Part 2 groundwork" pass, wired end-to-end on 0–100. Renaming to 0–1 would touch every layer for a purely cosmetic scale change with no functional benefit — both encodings are equally resolution-independent. What was actually missing/broken was the *letterbox* math: the click handler used the container's bounding rect, not the image's rendered rect, so coordinates were wrong whenever the image's aspect ratio didn't match its container (the near-universal case). Fixed via `computeContainRect()` + a `ResizeObserver`-driven `renderedRect` state in `AnnotationCanvas.tsx`; clicks in the letterbox padding are now ignored instead of creating a misplaced marker.
**Trade-off**: None functionally; if a literal `0..1` field name is ever required by an external contract, it's a pure rename at the API boundary, not a math change.

### DECISION-069: Reopen is brand-exclusive; agency resolves but never reopens
**Decision**: Added `POST /api/v1/brand-portal/annotations/{id}/reopen`, gated by `ctx.is_manager` (brand_owner/brand_manager), mirroring the existing `approve`/`request-revision` gating. The agency-side `POST /api/v1/annotations/{id}/reopen` (`deliverable_router`) now unconditionally returns `403` — it no longer performs the state change at all.
**Reason**: The first pass of this endpoint let *any* agency workspace member reopen a resolved revision with no role check (`_require_annotation` only checked `agency_id`, not who may act), while the intended business rule is: agency resolves, only an authorized brand user (owner/manager) reopens. Rather than adding a role check that could plausibly be relaxed later, the agency endpoint was changed to always deny — reopening is not an agency capability, full stop. The agency-side dashboard UI's "Yeniden Aç" button and its `annotationApi.reopen` client call were removed to match; the route itself is kept (not deleted) so an agency-originated reopen attempt gets an explicit `403` instead of a `404` that could be mistaken for a routing bug.
**Trade-off**: None — this is a strict narrowing of a capability that should never have been agency-accessible. Covered by `test_annotation_tenant_isolation.py::TestReopenAuthorizationMatrix` (agency 403, unauthorized brand role 403, authorized brand manager 200 as a positive control).

### DECISION-070: Annotation lifecycle events now dispatch through the existing notifier
**Decision**: `create_annotation`, `resolve_annotation`, `reopen_annotation`, `add_annotation_reply` (agency) and `create_brand_annotation`, `add_brand_annotation_reply`, the new brand `reopen` (brand) now call `NotificationDispatcher.emit(...)` with the existing fire-and-forget `try/except Exception: pass` pattern used elsewhere in this codebase (e.g. `submit_deliverable`). Added `NotificationEventType.ANNOTATION_REOPENED` (the other three annotation event types already existed in the enum, unused).
**Reason**: The enum values and dispatcher existed but were never actually wired into these endpoints — annotation activity produced no in-app/email/WhatsApp notification at all. Agency-authored, client-visible events notify brand members (`dispatcher.get_brand_members`); brand-authored events notify agency members (dispatcher's default `recipient_ids=None` resolution). Internal (`visibility="internal"`) annotations never notify the brand.
**Trade-off**: No ActivityLog entry was added per annotation event (unlike deliverable approve/revise) — comment-level activity wasn't previously logged there either, and per-annotation ActivityLog rows would add audit-trail noise disproportionate to a revision comment.

### DECISION-071: Two pre-existing DB bugs fixed while verifying against a live Postgres database
**Decision**: (a) `Deliverable.submitted_at`/`approved_at` changed from bare `DateTime` (naive) to `DateTime(timezone=True)`, migration `c9d0e1f2a3b4`. (b) `deliverable_annotations`/`annotation_replies`.`created_at`/`updated_at` were created `nullable=True` with **no** `server_default`, contradicting the SQLAlchemy `TimestampMixin` (`nullable=False, server_default=func.now()`); migration `d0e1f2a3b4c5` backfills NULLs and adds the missing default/constraint.
**Reason**: Both were discovered live: (a) crashed `submit_deliverable` with an asyncpg `DataError` ("can't subtract offset-naive and offset-aware datetimes") the moment a real submit was attempted; (b) a real annotation insert left `created_at=NULL` in Postgres, which then crashed `AnnotationRead`/`BrandAnnotationRead` response serialization (`created_at` is a required field). Neither had ever been exercised against a live database before — this repo's test suite is deliberately DB-agnostic (see DECISION-062), so schema/constraint mismatches like these are invisible to `pytest` and only surface under real Postgres.
**Trade-off**: None — both are corrective, backward-compatible migrations (backfill before constraint) with no data loss.

### DECISION-072: Playwright E2E added; annotation flow verified against a production build, not `next dev`
**Decision**: Added `@playwright/test`, `playwright.config.ts`, and `e2e/annotation-flow.spec.ts` (npm script `e2e`). The critical flow was verified by running `next build && next start` on a scratch port, not the ambient `next dev` server.
**Reason**: Against `next dev`, a hard page reload on a protected route occasionally bounced an authenticated session back to login — traced to React StrictMode double-invoking the refresh-session effect against a rotating refresh token, a dev-mode-only artifact unrelated to the annotation feature. Rather than reworking the shared auth-refresh flow (out of scope, real users don't hit dev-mode StrictMode), verification ran against a production build, which doesn't double-invoke effects. The spec still includes a one-retry `gotoAuthenticated()` helper as a `next dev` safety net for whoever runs it locally.
**Trade-off**: None functionally. (Superseded: an earlier version of this entry said IDOR/tenant-isolation coverage was manual-only — see DECISION-073, which replaced that with an automated live-DB harness.)

### DECISION-073: A first agency-side reopen review found no role check; added a live-DB test harness instead of trusting manual curl checks
**Decision**: (a) Fixed the vulnerability described in DECISION-069 (agency could reopen any resolved revision in its own tenant with no role check). (b) Added `app/tests/test_annotation_tenant_isolation.py`: a dedicated live-Postgres integration suite that builds real `Agency`/`Brand`/`User`/`AgencyMember`/`BrandMember`/`Brief`/`Deliverable`/`DeliverableAnnotation` rows for two independent tenants and drives the actual FastAPI app with real JWTs over `httpx.AsyncClient`, instead of relying on manual curl verification. Uses a disposable `flobrief_test` Postgres database (separate from the dev-compose `flobrief` DB, same local server; CI already provisions an equivalent throwaway container — see `.github/workflows/ci.yml`), created via `CREATE DATABASE flobrief_test` and `alembic upgrade head`; every fixture-created row is deleted in a `finally` block after each test (cascading via `ON DELETE CASCADE` from `Agency`/`Brand`).
**Reason**: A prior draft of this feature (see the now-corrected DECISION-069/-072 text) treated "manually curl'd it once against two tenants" as equivalent to an automated regression test. It was not: the agency-side reopen endpoint had exactly zero authorization check beyond tenant membership, and no automated test caught it. The new suite asserts the full matrix requested during review: cross-tenant list/reply/resolve/reopen denial (404 or 403), same-tenant-but-wrong-deliverable annotation-ID reuse (404), the reopen role matrix (agency 403, brand_viewer 403, brand_manager 200), and brand-portal cross-tenant isolation — plus positive controls (agency resolve/reply still succeed) so a blanket "always deny" bug wouldn't silently pass the denial assertions.
**Trade-off**: Requires a real Postgres reachable at `$DATABASE_URL` to run (skipped/erroring otherwise, same precondition as any Alembic migration work) — accepted because schema-level bugs in this feature (DECISION-071) were already proving that DB-agnostic tests can't see real authorization or constraint regressions. This one test file is the exception to the repo's DB-agnostic convention (DECISION-062), scoped narrowly to the annotation/reopen surface rather than a wholesale harness rewrite.

### DECISION-074: Real-time notifications use one-time Redis tickets and post-commit change signals
**Decision**: Agency and brand clients obtain a 60-second, single-use Redis ticket over their existing authenticated REST surface, then connect to one shared `/api/v1/notifications/realtime` WebSocket. Redis pub/sub fans tenant-scoped `notifications.changed` signals to every backend worker. The SQLAlchemy session queues signals and publishes them only from `after_commit`; rollback clears the queue. The browser refetches the canonical notification feed on a signal and retains 45-second polling as a recovery path.
**Reason**: Putting a reusable JWT in a WebSocket query string would expose it to proxy and access logs. In-memory-only connection state would also fail as soon as production runs multiple API workers. Publishing before the business transaction commits could reveal rolled-back notifications or race the subsequent feed request. A short, one-use ticket, post-commit signal, and Redis fan-out address all three risks while keeping the database as the source of truth.
**Trade-off**: Redis is required to establish a live connection, so ticket issuance fails closed with HTTP 503 when Redis is unavailable. Core notification behavior remains available through REST polling, and missed ephemeral signals are repaired on the next poll, reconnect, tab visibility change, or network recovery.

### DECISION-075: Route uniqueness is a release invariant; brand assets have an explicit visibility boundary
**Decision**: Every registered FastAPI HTTP method/path pair must be unique, enforced by `test_route_uniqueness.py`. The two duplicate brand-portal brief-asset GET/POST registrations were replaced by one canonical pair. Brand lists return only `client_visible` and `brand_reference` assets linked to their own brief; brand deletion accepts only a `brand_reference` asset owned by that brand. Upload state validation, image metadata, notification dispatch, and failed-transaction storage cleanup live in `AssetService`.
**Reason**: FastAPI accepts duplicate registrations and dispatches the first match, leaving later “improved” handlers unreachable. In this case the reachable handler bypassed the intended brief-state rules, while both list implementations could expose agency-internal assets and deletion scoped only to the agency. A global uniqueness assertion prevents silent shadow routes, and explicit visibility/ownership checks make the brand boundary reviewable in one service.
**Trade-off**: Brand users cannot delete agency-provided `client_visible` assets; agencies retain ownership of those files. Local storage cleanup is best-effort if the database transaction fails and logs an operational error if the storage backend itself cannot delete the orphan.

### DECISION-076: Documentation describes implemented production behavior, not planned adapters
**Decision**: Environment and deployment documentation now treats local persistent storage as the only implemented backend, Resend HTTPS as the email path, encrypted DB-backed Twilio as the WhatsApp path, port 8000 as the local API standard, and port 5433 as the local PostgreSQL host mapping. Next standalone output is enabled only when `DOCKER_BUILD=true`, and Node 20.x is the supported frontend runtime.
**Reason**: Previous documents advertised S3 selection without an implementation, instructed operators to configure nonexistent SMTP variables, and disagreed on ports. The Next configuration also claimed standalone was Docker-only while enabling it for every non-Vercel local build. Operational documentation must be an executable contract; roadmap capabilities and historical decisions remain documented separately.
**Trade-off**: Deployments using local media storage cannot safely scale across hosts without shared durable storage. S3/R2 remains an explicit roadmap item rather than a misleading environment toggle.

### DECISION-077: Public demos use isolated expiring tenants, never shared credentials
**Decision**: Every public `/demo` request creates a unique agency, owner user, refresh session, and seeded sample workspace. The agency and sandbox both carry the expiry boundary; access checks reject an expired session immediately, while a scheduler suspends the tenant, disables its user, and revokes refresh tokens. Creation is disabled by default and protected by a global capacity, durable HMAC-hashed per-IP daily quota, and optionally required Cloudflare Turnstile verification.
**Reason**: A shared sales account leaks changes between prospects, cannot provide reliable tenant isolation, and is difficult to reset safely. Isolated disposable tenants provide a realistic product experience without sharing data or long-lived credentials. Hashing the source IP preserves durable abuse control without storing the raw address in the demo audit table.
**Trade-off**: Each demo consumes temporary database rows and requires scheduled cleanup. Operators must configure Turnstile and capacity limits before public activation.

### DECISION-078: Demo operations are centrally managed and excluded from commercial truth
**Decision**: `/platform/demo` is the control plane for activation, duration, concurrent capacity, daily IP quota, CAPTCHA policy, cleanup, and manual termination. Demo tenants may exercise ordinary product workflows, but invitations, billing, payments, accounting connectors, e-mail, and WhatsApp side effects are blocked or skipped. Demo agencies, users, and subscriptions are excluded from the normal platform agency/brand/user lists, customer analytics, plan distribution, subscription count, and MRR.
**Reason**: A public sandbox must be safe to explore without contacting real people, creating financial side effects, or distorting management reporting. Keeping demo lifecycle data in its own platform view gives operators visibility while maintaining one trustworthy set of commercial metrics.
**Trade-off**: Product paths with genuine external integration behavior still require a controlled sales or staging demonstration; the public sandbox intentionally shows the interface without sending those side effects.

### DECISION-079: The critical Playwright release matrix runs against an isolated production build and current realtime backend
**Decision**: `npm run e2e:critical` defines the 42-test release matrix across authentication, brief workspace, annotation/revision/approval, calendar, platform administration, mobile brand flows, notification deep-links, and realtime WebSocket behavior. Verification uses a Node 20 production Next build on an isolated port, a separately started current FastAPI process, PostgreSQL/Redis, and an explicit build-time `NEXT_PUBLIC_WS_URL`; it does not reuse an ambient development frontend or a stale backend process.
**Reason**: An ambient API on port 8003 was healthy but older than the checked-out source, so newly added realtime-ticket routes returned 404. Next's HTTP rewrite also does not represent the production WebSocket upgrade path. Isolating both application processes and setting the WebSocket origin explicitly makes the release result attributable to the current source state. The run also exposed two fixture regressions: onboarding could appear after a synchronous visibility check, and a reference asset still relied on pre-hardening visibility behavior.
**Trade-off**: The matrix requires a production build and explicit test ports, so it is slower than development-server smoke tests. Fixture seed scripts write temporary rows to the local non-production database and must retain their cleanup behavior.

### DECISION-080: Local development uses the canonical API port and Turbopack, with Webpack retained as a fallback
**Decision**: Normal local development leaves `NEXT_PUBLIC_API_URL` empty so the same-origin Next rewrite targets FastAPI on port 8000. The E2E-only `E2E_REWRITE_API_PORT` override is not persisted in `.env.local`. `npm run dev` uses Turbopack, while `npm run dev:webpack` remains an explicit compatibility fallback. Global CSS imports must precede Tailwind directives, and dynamic home metadata abandons an unreachable backend after 1.5 seconds.
**Reason**: A stale local override directed every frontend API request to an inactive port 8003. Separately, Webpack required 9.1 seconds to compile the home route from a clean cache. Turbopack reduced that cold request to 4.9 seconds and the login route from 2.48 seconds to 0.66 seconds, but initially exposed an invalid mid-file CSS import that Webpack had tolerated. Correcting both configuration and CSS ordering removes the persistent wait and makes the faster compiler safe.
**Trade-off**: The first visit to an uncompiled route still performs development-only compilation and is slower than a production build. Turbopack behavior can differ from Webpack, so the compatibility command and the mandatory Node 20 production build remain part of the verification path.

## Part 6A (continued) — Free Local Twilio Sandbox Freeform Test Mode

### DECISION-081: Dev-only Sandbox freeform fallback, gated on the official Twilio Sandbox sender rather than just `provider_type`
**Decision**: When no approved Content Template exists yet, `whatsapp_test_send_service._sandbox_freeform_test_eligible()` allows a one-off free-text send via the existing `POST /api/v1/notifications/whatsapp/test` endpoint, but only when every one of: `APP_ENV=="development"`, `WHATSAPP_NOTIFICATIONS_ENABLED`, the new `WHATSAPP_SANDBOX_FREEFORM_TEST_ENABLED` flag, `TwilioWhatsAppProvider.is_official_sandbox_sender()` (the configured `from` number matches Twilio's fixed public Sandbox sender `whatsapp:+14155238886` exactly, not merely `provider_type=="twilio_sandbox"`), and `WHATSAPP_TEST_RECIPIENT` being set. The message body is a fixed constant (`TwilioWhatsAppProvider.SANDBOX_FREEFORM_TEST_BODY`); no caller input ever reaches it. Demo-tenant, consent, and Owner/Admin-only RBAC gates from the existing flow are unchanged and still apply upstream of this fallback.
**Reason**: A real Twilio Sandbox session accepts free-text messages without a Meta-approved Content Template, which is what makes it useful for verifying a connection before any template has been approved — but `provider_type=="twilio_sandbox"` is an operator-set DB field, not proof the sender is actually Twilio's shared sandbox number. ## Part 6B-1 — WhatsApp domain event routing

### DECISION-082: NotificationDispatcher's WhatsApp branch now requires an approved registry template; the old per-event freeform sender was removed
**Decision**: `NotificationDispatcher._dispatch_whatsapp` replaces the previous `_build_whatsapp_body`/`whatsapp_templates` freeform-string path (which called `TwilioWhatsAppProvider.send_message` with hand-built Turkish text for every event, in every environment, including production). It now: (1) computes a deterministic `idempotency_key = f"{event.id}:{recipient_id}:whatsapp"` (event.id alone already determines event_type via FK, so it's omitted to stay safely under the column's 100-char limit for every event_type length) and skips if a delivery already exists for it; (2) checks demo tenant / consent / phone in that order (`skipped_demo_tenant` / `skipped_no_consent` / `skipped_no_phone`); (3) looks up `app.services.whatsapp_event_catalog.get_event_definition(event_type)` for a `template_key`; (4) applies `whatsapp_recipient_gate.is_whatsapp_role_eligible` (role narrowing, see DECISION-083); (5) calls `WhatsAppTemplateRepository.get_approved(template_key)` — `None` (missing/draft/pending/disabled/no content_sid) always yields `skipped_template_missing`, never a fallback send; (6) on an approved template, builds variables via `whatsapp_payload_builder.build_variables`/`map_to_content_variables` and calls `send_template_message(phone, content_sid, content_variables)` — never `send_message` (freeform). The dev-only Sandbox freeform fallback (DECISION-081) is untouched and lives only in `whatsapp_test_send_service`, never reachable from this path.
**Reason**: The freeform path was a live production-safety gap — it sent real, uncontrolled Turkish text for `brief.submitted_for_approval`, `comment.added`, `deliverable.*`, etc. regardless of `APP_ENV`, which Part 6A's approved-template requirement never actually applied to. Routing every domain event through the same registry gate as the test-send flow closes that gap and gives operators one place (`whatsapp_templates.status`) to control what can ever leave the system.
**Trade-off**: Until an operator flips a template row to `approved` with a real Content SID, that event's WhatsApp channel silently degrades to `skipped_template_missing` — in-app and email are unaffected (verified in `test_whatsapp_event_dispatch.py`), but no WhatsApp message goes out for any of the 16 seeded template codes today. This is intentional (DECISION-087 template-code seeding, below) rather than a regression: no code was flipped to `approved` by this migration.

### DECISION-083: WhatsApp-only recipient narrowing lives in one gate function, layered on top of (not replacing) each domain service's existing recipient resolution
**Decision**: `whatsapp_recipient_gate.is_whatsapp_role_eligible(db, event, user)` narrows exactly two catalog events beyond what the domain service already resolved for in-app/email: `BRIEF_SUBMITTED` ("approval.requested") requires the brand recipient to hold `Permission.BRIEF_APPROVE` for that brief's brand; `INVOICE_PAYMENT_RECEIVED` requires the agency recipient to hold `Permission.INVOICE_VIEW` for that agency. Every other event returns `True` unconditionally — no extra query, no behavior change. The check is fail-closed: no resolvable membership row for the event's `agency_id`/`brand_id` means ineligible, not eligible.
**Reason**: Every other domain service (comment_service, mention_service, deliverables.py, client_invoice_service, finance_capacity_scheduler) already resolves the correct in-app/email recipient set correctly (verified while inspecting each call site) — rebuilding recipient resolution from scratch per the task brief's instruction not to scatter it further would have duplicated already-correct logic. The two exceptions are the only places the task's role rules (approver-only, invoice:view-only) are stricter than the existing shared recipient list, which intentionally also includes brand_viewer/other roles for the visibility of the in-app nudge.
**Trade-off**: If a future WhatsApp event needs its own role narrowing, it must be added explicitly to one of the two lookup dicts in this module — there is no generic per-role-per-event config table. Acceptable at 16 events; would need revisiting past a few dozen.

### DECISION-084: WhatsApp template variables are allowlisted by name, never by raw payload passthrough
**Decision**: `whatsapp_payload_builder.ALLOWED_VARIABLE_FIELDS` is the closed set of ten names (`recipient_first_name`, `actor_display_name`, `brief_title`, `brand_name`, `deliverable_title`, `due_date`, `invoice_number`, `invoice_total_formatted`, `short_safe_summary`, `deep_link_url`) any template may ever reference. `build_variables()` always returns exactly this key set; `map_to_content_variables()` drops any `WhatsAppTemplate.variable_schema` entry naming a field outside it before building Twilio's `{"1": ..., "2": ...}` ContentVariables payload. `short_safe_summary` is the only free-text-derived field — always routed through `short_safe_preview()` (HTML-tag strip, whitespace collapse, hard 80-char truncate) over `comment_preview`/`reason`/`summary`, never the full comment/annotation/revision body (those were never stored in `NotificationEvent.payload` in full to begin with — verified in `comment_service.py`/`deliverables.py`/`brand_portal.py`).
**Reason**: The task requires that no cost/rate/credential/internal-note value, full comment/revision text, or arbitrary caller-controlled key can ever reach a WhatsApp send, and that a caller cannot rename which payload field lands on which template placeholder. A fixed allowlist plus a schema→field indirection (rather than passing `event.payload` straight through) makes both guarantees structural rather than convention-based.
**Trade-off**: Any new information a future template needs must be added to the allowlist deliberately — this is the intended friction, not an oversight.

### DECISION-085: Deep links pick the agency or brand portal path from the recipient's own account type, never from event data
**Decision**: `whatsapp_payload_builder.resolve_deep_link` branches on `recipient.user_type` (not on anything in `event.payload`) to choose `dashboard/*` vs `brand/*` URL prefixes, then appends the entity path/query params (`?panel=comments`, `?deliverable=`, `?annotation=`) that `apps/frontend/app/dashboard/briefs/[id]/page.tsx` already consumes for its existing notification deep-link handling (unchanged, no frontend work needed). `UrlBuilder` gained `brief_comments`, `deliverable_detail`, `annotation_detail`, `invoice_detail`, and a `brand_side` flag on `notification_preferences` — all built from `FRONTEND_PUBLIC_URL` and server-resolved UUIDs already on the payload, never from request input.
**Reason**: A link that ignored the recipient's account type could point a brand user at the agency dashboard (or vice versa), which their own permission check would then correctly reject — technically "safe" but a broken experience. Branching on the recipient row rather than trusting a payload flag closes that class of bug at the source.
**Trade-off**: None — purely additive to `UrlBuilder`; no existing method signature changed.

### DECISION-086: Four gaps in the WhatsApp event catalog required new `NotificationEventType` members and small, targeted wiring — not a second notification system
**Decision**: Added `BRIEF_ASSIGNED`, `BRIEF_OVERDUE`, `INVOICE_DUE_SOON`, `INVOICE_PAYMENT_RECEIVED` to the existing `NotificationEventType` enum (plain `String(50)` column, no DB migration needed for the enum itself). Each routes through the existing `NotificationDispatcher.emit()` — no parallel dispatch path: (a) `brief.assigned` emits from `POST /briefs/{id}/participants`, recipient the new assignee only; (b) `brief.overdue` is a new `run_overdue_check()` in `deadline_scheduler.py`, sharing `_REMINDER_EXCLUDED_STATUSES` (archived/approved/completed/rejected) and the existing 23h dedupe pattern with the pre-existing due-soon check; (c) `invoice.due_soon` is a new `_check_invoice_due_soon` in `finance_capacity_scheduler.py`, mirroring `_check_invoice_overdue`'s shape but notifying the brand (client) instead of the agency, with a `due_date >= today` / `< today` split against `_check_invoice_overdue` guaranteeing the two never both fire for the same invoice on the same day; (d) `invoice.payment_received` emits from `PaymentService.record_payment` only when a payment brings `amount_paid_cents >= total_cents` (not on partial payment), to agency members holding `invoice:view` (DECISION-083).
**Reason**: The task's 16-event catalog named these four explicitly; 12 of the 16 already had a correctly-wired `NotificationEventType` and emit call site discovered during the Section 1 codebase inspection, so only these four needed new plumbing.
**Trade-off**: `brief.due_soon` in the task's catalog maps to the pre-existing `CALENDAR_ITEM_DUE` event type (deadline_scheduler's original due-soon check) rather than a new enum member — reusing it avoids a second "brief is due soon" concept; the WhatsApp catalog's `template_key="brief_due_soon"` is what's new, not the underlying domain event.

### DECISION-087: The 16 WhatsApp template codes are seeded via one idempotent Alembic migration, all `status=draft`, `content_sid=NULL`
**Decision**: Migration `n8o9p0q1r2s3` (chained after Part 6A's `f3g4h5i6j7k8`) bulk-inserts one row per `template_key` in `whatsapp_event_catalog.WHATSAPP_EVENT_CATALOG` into `whatsapp_templates`, following the exact shape of Part 6A's `flobrief_test_notification` seed: `provider="twilio"`, `language_code="tr"`, `content_sid=NULL`, `status="draft"`, `variable_schema={}`, and a reference `body` documenting the intended Twilio placeholder layout. `revision_requested` and `mention_created` are each shared by two `NotificationEventType`s (brief/deliverable revision; comment/annotation mention) — one template row, one `code`, looked up by `template_key` not `event_type`.
**Reason**: `WhatsAppTemplateRepository.get_approved()` already refuses anything not `status=approved` with a `content_sid` — seeding `draft` rows makes every one of the 16 events immediately exercise the real `skipped_template_missing` path (verified in tests) rather than crash on a missing-row lookup, while guaranteeing no fabricated "approved" template ever ships from a migration.
**Trade-off**: An operator must manually register each real Meta/Twilio Content Template and flip `status`/`content_sid` before any of these 16 events can actually reach a phone — deliberate, matches the existing `flobrief_test_notification` precedent and the task's explicit "hiçbir kayıt sahte şekilde approved oluşturulmasın" constraint.

## Production delivery — GitHub Actions to Hetzner

### DECISION-088: Only the exact green `main` commit may be promoted automatically
**Decision**: The existing CI workflow owns Hetzner promotion as a third job that depends on both backend and frontend gates. It is restricted to pushes on `main`, a protected `production` environment, strict SSH known-host verification, a concurrency lock, and the explicit `HETZNER_DEPLOY_ENABLED=true` repository variable. The server-side script verifies the expected GitHub remote and tested SHA, refuses a dirty checkout, backs up PostgreSQL/media, requires one Alembic head, builds SHA-tagged images, applies migrations, waits for container/public health, and records the successful release. It attempts only an application-image rollback; schema downgrade or database restore is never automatic.
**Reason**: A server-side `git pull && docker compose up` would deploy unverified moving state, allow overlapping releases, and provide no durable pre-migration recovery point. Tying promotion to the already-required quality gates makes the deployed SHA auditable while preserving tenant data and local media.
**Trade-off**: Initial server/DNS/TLS/SSH/GitHub environment setup remains a deliberate manual operation. On-host backups improve immediate recovery but do not satisfy the required off-host backup and restore-drill policy.

### DECISION-089: Production Resend credentials are environment-authoritative and all transactional mail shares one safe delivery path
**Decision**: When `APP_ENV=production` and `RESEND_API_KEY` plus `EMAIL_FROM` are present, the environment-backed Resend REST provider is authoritative even if an `email_resend` DB row exists. Without that production secret, an enabled and decryptable DB row may provide delivery; outside production the enabled DB row remains first and environment config is fallback. Verification, verification resend, password reset, invitations, invitation resend, and notification email all resolve the provider through `EmailProviderFactory`. Delivery logs contain provider, message type, status, safe error category/type, and never recipient content, tokens, or credentials.
**Reason**: The old presence-based precedence let any disabled, incomplete, undecryptable, or stale enabled DB row suppress or replace a valid production server credential. Auth and invitation services also swallowed every provider exception, making delivery failures invisible. Production environment authority makes secret rotation and incident recovery deterministic, while a shared non-throwing delivery boundary preserves enumeration-resistant auth responses and records operationally useful failures without leaking the API key.
**Trade-off**: While the production environment key exists, changing or disabling the DB row does not change effective delivery. Operators must rotate/remove the server secret to transfer authority to the DB-backed provider; the platform screen exposes the effective configuration source to make this explicit.

## Public SEO landing pages

### DECISION-090: SEO pages share one server-rendered marketing system and remain indexable without backend availability
**Decision**: The five intent-specific Turkish landing routes use static App Router pages, per-route Metadata API declarations, one shared responsive public header/footer, config-driven content, and five distinct product UI visualizations derived from verified product flows. `sitemap.ts` merges these routes into its output after the optional backend SEO response, so they remain discoverable when the backend is unavailable. Only the mobile menu is a Client Component; no landing page fetches data or adds an API route.
**Reason**: Search content must exist in HTML without client JavaScript, direct visitors need full public navigation, and the routes must not disappear from the sitemap because an unrelated service is temporarily unreachable. Shared shell and design tokens keep the pages consistent while route-specific copy, section order, workflow, and visual treatment prevent duplicate-page design.
**Trade-off**: The five route modules are intentionally thin wrappers over one content registry. Future product changes that invalidate a marketing claim must update that registry and its Chromium regression expectations together.

### DECISION-091: Public login is modal-first and platform entry is never advertised by public UI or tenant auth
**Decision**: All public login triggers open one shared accessible dialog without route navigation. The compatibility login entry route opens that dialog immediately and retains only a validated internal return target. Public navigation, footer, selector copy, and tenant-auth errors contain no platform administration URL or role-specific routing hint. Platform responses additionally carry search exclusion, no-store, frame-denial, and no-referrer headers, while public robots output always disallows the platform route.
**Reason**: A stable modal keeps the public journey consistent, while removing route disclosure reduces unnecessary discovery and phishing guidance. Real authorization remains the security boundary: tenant-independent role validation, shorter platform tokens, rate limits, MFA support, optional IP allowlisting, and audit logs continue to protect the backend even if an attacker guesses a route.
**Trade-off**: Route secrecy is defense-in-depth, not authentication. Production currently has no platform IP allowlist and the two active platform administrators have not enrolled MFA; enforcing either before trusted-IP and recovery testing could lock out legitimate operators, so those controls remain an explicit operational release task.

### DECISION-092: English is canonical at unprefixed URLs and Turkish uses a stable `/tr` public prefix
**Decision**: The UI uses one typed, complete EN/TR message catalog and an application locale provider. Unprefixed public URLs are English; Turkish public URLs use `/tr`, with manual cookie choice taking priority over signed-in profile locale, browser language, country signal, and the English fallback. A stored user locale drives authenticated UI, email, and notification rendering. Public language changes preserve the equivalent route and publish localized canonical/hreflang metadata.
**Reason**: Stable crawlable URLs avoid content ambiguity, while the explicit precedence keeps a user's choice consistent across anonymous, authenticated, browser, and transactional surfaces.
**Trade-off**: The legacy Turkish home composition remains visually distinct from the new English home, but both expose the same language control and public navigation contract.

### DECISION-093: The premium Turkish home composition is the single visual source for both locales
**Decision**: The existing animated Turkish home remains intact and now renders in both locales from the same React component tree. A dedicated English copy map translates its hero, navigation, product scenes, lifecycle, persona panels, trust area, calls to action, and footer without selecting a second page component. The compact language selector keeps its footprint while using inline SVG Turkish and English flags, localized accessible labels, and the existing route-preserving locale switch.
**Reason**: Locale must be content state, not a different design. One component tree guarantees that section order, cards, animations, breakpoints, spacing, and interaction behavior cannot drift when the user switches language.
**Trade-off**: English sentences naturally wrap differently from Turkish at narrow widths, but no visual component, class hierarchy, or responsive landmark changes; Chromium regression coverage compares both locale structures directly.

### DECISION-094: Public and login surfaces share the supplied PostPiloter master logo
**Decision**: The supplied transparent `PostPiloter_Logo.png` is stored as the versioned public asset `/postpiloter-logo.png` and rendered through one `PostPiloterLogo` component. The shared rich home, public SEO header/footer, pricing header, login modal, compatibility login route, and shared auth card use this component at surface-appropriate heights. EN/TR structure tests assert the real image in navigation and reject the obsolete `Flobrief` label.
**Reason**: Reusing the legacy page composition must not reintroduce its pre-rebrand placeholder identity or make the real brand logo appear deleted. A single component keeps the exact supplied artwork, intrinsic aspect ratio, accessible text, and responsive sizing consistent across both locales.
**Trade-off**: The 98 KB PNG is intentionally served as the supplied master artwork and optimized by Next.js. If a vector master becomes available later, the shared component and one asset can be updated without changing individual page structures.

### DECISION-095: Paddle-review legal routes are localized, crawlable, and share one legal-page system
**Decision**: `/terms`, `/privacy`, `/refund-policy`, and `/contact` use one typed legal configuration and shared public shell. English remains canonical at unprefixed URLs and Turkish uses `/tr`; each route publishes a unique localized title, description, canonical, hreflang, and Open Graph record. The sitemap and public footer expose both locale variants. Paddle is identified as Merchant of Record in the requested billing disclosures, while contact sections expose direct mail links instead of display-only labels.
**Reason**: Payment-provider review requires discoverable policy and contact pages, but repeated page markup and placeholder metadata would create drift and weak crawl signals. One system keeps design, locale behavior, contact paths, and policy navigation consistent while allowing policy-specific content.
**Trade-off**: This release publishes operational policy text, not legal advice or a substitute for counsel. Policy wording, dates, supported mailboxes, Paddle account status, consumer-law obligations, and actual processor/subprocessor behavior must be kept aligned with production operations whenever those facts change.
